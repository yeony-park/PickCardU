### 3.3 OCR 품질 진단

다음 수치는 기존 Luna 결과와 새 Luna 결과가 모두 있는 동일한 104개 문서만 비교했다. Upstage는 정답표가 아니라 차이를 찾기 위한 고정 비교 대상으로 사용했다.

| 지표 | 기존 Luna | 새 Luna | 변화 | 해석 |
|---|---:|---:|---:|---|
| Luna 본문 문자 수 | 835,556 | 871,903 | +36,347 (+4.35%) | 상세 프롬프트에서 출력 문자 수 증가 |
| 평균 문서별 token Jaccard | 0.848856 | 0.848017 | -0.000839 | 사실상 동률 수준의 소폭 하락 |
| Upstage 숫자 기준 Luna 숫자 재현율 | 0.968523 | 0.969414 | +0.000891 | 숫자 일치는 소폭 상승 |
| 새 Luna 불확실 표시 | 해당 없음 | 2개 | 비교 불가 | 판독 불가 문자를 추측하지 않고 `�`와 사유로 기록 |

**지표 설명**

- `token Jaccard`는 Luna와 Upstage에서 나온 서로 다른 단어 집합의 겹침 비율이다. 예를 들어 둘 다 `편의점 10% 할인`을 읽으면 높아진다. 먼저 한 문서 안의 페이지 값을 평균하고, 다시 동일한 104개 문서의 값을 평균했다. 높을수록 두 OCR이 비슷하지만, 둘 다 같은 오독을 해도 높을 수 있어 정답률은 아니다.
- `숫자 재현율`은 Upstage가 읽은 서로 다른 숫자 중 Luna에도 있는 비율이다. 예를 들어 Upstage의 `전월 30만원, 월 1만원` 중 Luna가 두 숫자를 모두 읽으면 100%다. Upstage가 휴대전화 화면이나 디자인 속 숫자를 잘못 읽으면 Luna가 정확해도 낮아질 수 있다.

가장 낮은 숫자 재현율 문서는 `Kookmin_AlphaOne_20210923`의 64.52%였다. 원문과 양쪽 OCR을 확인한 결과, 차이의 대부분은 Upstage가 안내 이미지 속 시각·마스킹 카드번호·화면 숫자를 읽은 데서 발생했다. 이 값만으로 Luna가 혜택 숫자를 누락했다고 판정하지 않았다.

상세 프롬프트는 텍스트량과 숫자 일치를 소폭 늘렸지만, 전반적인 OCR 정확도가 확실히 향상됐다고 단정할 수 없다. 사람 검수용 gold가 없으므로 위 수치는 진단용이다.

## 6. 결론과 다음 단계

- Upstage 원응답은 106개·617쪽 모두 API 재호출 없이 새 형식으로 파싱됐다.
- Luna는 106개 중 104개가 성공했고, 페이지 fallback이 실제 전수 실행에서 3개 문서를 복구했다.
- `NH_SOHO_Dasaroi_OIL` API timeout과 `Hyundai_The_Orange` 비어 있는 비-빈 페이지 미복구가 남아 있다.
- Upstage `is_blank`가 617쪽 전체에 잘못 기록되는 파서 오류가 발견됐다.
- 새 Luna 프롬프트는 텍스트량과 숫자 일치를 소폭 늘렸지만 전반적인 정확도 향상을 확정할 근거는 없다.
- 현재 설정의 확인 가능한 누적 Luna 비용은 `$5.301535`이고, 106개 배치 wall time은 약 2시간 9분이다.
- **OCR 결과에 문제가 있으므로 `structure` 단계로 진행하지 않았다.**

다음 승인 범위는 다음 세 작업으로 제한한다.

1. Upstage `is_blank` 표시와 Luna의 비어 있는 비-빈 페이지 fallback 판정을 수정하고 단위 테스트한다.
2. Upstage 106개는 외부 호출 없이 다시 파싱한다.
3. Luna는 실패한 두 문서만 재호출해 106/106 페이지 무결성을 다시 확인한다.

세 작업이 모두 통과한 뒤에만 별도 조건에 따라 `structure` → `normalize` → `validate`를 진행한다.
