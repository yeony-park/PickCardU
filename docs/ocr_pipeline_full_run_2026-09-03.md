### 3.3 OCR 품질 진단

최종 106개 결과를 동일한 Upstage 출력과 비교했다. Upstage는 정답표가 아니라 차이를 찾기 위한 고정 비교 대상이다.

| 지표 | 최종 결과 | 해석 |
|---|---:|---|
| Luna 본문 문자 수 | 891,444 | 실제 빈 면 정규화 후 106개 전체 합계 |
| 평균 문서별 token Jaccard | 0.850596 | 양쪽 OCR의 단어 겹침 진단값 |
| Upstage 숫자 기준 Luna 숫자 재현율 | 0.962503 | Upstage 숫자 중 Luna에도 있는 비율 |
| 페이지 배열 무결성 | 617/617쪽 | 누락·중복·순서 오류 0건 |
| 비어 있는 비-빈 페이지 | 0쪽 | 구조화 차단 조건 해소 |

**지표 설명**

- `token Jaccard`는 Luna와 Upstage에서 나온 서로 다른 단어 집합의 겹침 비율이다. 예를 들어 둘 다 `편의점 10% 할인`을 읽으면 높아진다. 먼저 한 문서 안의 페이지 값을 평균하고, 다시 106개 문서의 값을 평균했다. 높을수록 두 OCR이 비슷하지만, 둘 다 같은 오독을 해도 높을 수 있어 정답률은 아니다.
- `숫자 재현율`은 Upstage가 읽은 서로 다른 숫자 중 Luna에도 있는 비율이다. 예를 들어 Upstage의 `전월 30만원, 월 1만원` 중 Luna가 두 숫자를 모두 읽으면 100%다. Upstage가 휴대전화 화면이나 디자인 속 숫자를 잘못 읽으면 Luna가 정확해도 낮아질 수 있다.

상세 프롬프트의 전반적인 OCR 정확도가 향상됐다고 단정할 수는 없다. 사람 검수용 gold가 없고 Upstage도 오독할 수 있으므로 위 수치는 진단용이다. 이번 단계의 통과 기준은 두 OCR의 완전한 일치가 아니라, 106개 문서의 페이지 무결성과 구조화 전에 자동 검출 가능한 빈 본문·빈 면 오류가 없는 것이다.

#### 7.7.4 근본 원인

1. **프롬프트와 검증 규칙이 직접 충돌한다.** 프롬프트는 다른 줄의 조건·예외를 합치지 말고 그 문구 자체를 별도 fact로 만들라고 한다. 반면 검증기는 모든 fact에 비어 있지 않은 `target`을 요구하고, 비어 있지 않은 모든 필드가 하나의 quote 안에 문자 그대로 있어야 한다. 예를 들어 `1 카드사의 휴업·파산...`이라는 예외 줄을 별도 fact로 만들면 `exceptions`는 채울 수 있지만 같은 줄에 혜택 대상이 없어 `target`은 비게 된다. 실제 빈 target 2,870건 중 `exceptions`만 채운 경우가 1,783건으로 가장 많았다.
2. **JSON Schema는 형식만 강제하고 의미 조건은 강제하지 않는다.** `target`, `condition`, `value` 등은 모두 문자열 타입이면 되므로 빈 문자열도 strict schema를 통과한다. 반면 후속 검증기는 target이 비어 있거나 target 외 내용이 없으면 실패시킨다. 따라서 “API가 strict JSON을 정상 반환했다”와 “검증 가능한 fact를 만들었다”가 일치하지 않았다.
3. **제목과 설명 줄을 fact로 과도하게 만들었다.** `부가서비스 안내`, `청구할인 서비스` 같은 제목을 target만 있는 fact로 만들었다. 이 때문에 target 외 내용이 없는 fact가 593건 생겼다. 제목은 section metadata나 disposition으로 남겨야지 독립 혜택 fact로 보면 안 된다.
4. **모든 OCR 줄을 LLM이 다시 복사하게 한 방식이 지나치게 취약하다.** 표, 줄바꿈, 글머리표가 있는 긴 문서에서 모델이 공백을 바꾸거나 인접 줄을 합치면 exact-line 검증에 실패한다. 예를 들어 OCR의 긴 안내 문구를 disposition에서 띄어쓰기만 다르게 복사해도 해당 줄은 “정확한 줄이 아님”과 “원 OCR 줄 미배치”로 동시에 잡힌다. 줄 자체를 다시 쓰게 하기보다 입력에 안정적인 line ID를 붙이고 ID만 분류하게 하는 편이 적합하다.
5. **혜택 누락 방지 정규식이 너무 넓다.** 현재는 ignore 줄에 `할인`, `적립`, `마일`, `포인트`, `혜택` 등이 들어가면 일부 법정 문구를 제외하고 재구조화를 요구한다. 실제로 `카드 이용 시 제공되는 추가적인 혜택 등 부가서비스 제공에 소요된 비용` 같은 법정 안내와 `대상 | 적립율` 같은 표 머리글도 걸렸다. 일부는 실제 중요한 조건일 수 있지만 1,394건 모두를 혜택 누락이라고 볼 수는 없다. 현재의 7개 차단 문서는 이 규칙까지 검증이 진행되어 첫 오류로 노출된 문서 수일 뿐이다.
6. **실제 grounding 문제도 존재한다.** 단순히 검증기가 엄격한 것만이 원인은 아니다. `매일 할인 7% 배달앱`처럼 OCR에 그대로 이어져 있지 않은 문구를 quote로 조합하거나, quote에는 없는 target·기간·한도를 채운 사례가 있다. 이런 경우는 카드 간 혜택 혼합과 수치 환각을 막기 위해 계속 차단해야 한다.
7. **normalize 단계가 오류를 만든 것은 아니다.** 현재 normalize는 구조화 결과의 `identity`, `facts`, `span_dispositions`를 OCR pages와 provenance에 묶어 저장할 뿐, fact 값을 재작성하지 않는다. 이번 실패는 구조화 출력과 검증 계약 사이에서 발생했다.

#### 7.7.5 판정

- 자동 통과 0건의 주원인은 **OCR 전수 실패가 아니라 구조화 프롬프트·schema·검증 규칙의 불일치와 문서 단위 all-or-nothing 판정**이다.
- `99개 검토 필요`와 `7개 재실행 필요`를 실제 오류 종류가 두 개뿐이라는 뜻으로 해석하면 안 된다. 이는 문서별 첫 중단 상태이며, 독립 진단에서는 여러 오류가 중첩됐다.
- 현재 결과를 그대로 승인하거나 인덱싱해서는 안 되지만, 212개 전체를 같은 설정으로 다시 호출해도 같은 유형의 실패가 반복될 가능성이 높다.
- 우선 prompt와 schema가 validator와 같은 fact 단위를 사용하도록 맞추고, OCR 줄은 line ID 기반으로 분류하며, 혜택 ignore 규칙의 오탐을 분리해야 한다. 이후 대표 오류 문서 5~10개에서 재구조화하여 자동 통과 여부와 실제 혜택 보존을 함께 확인한 뒤 전수 재실행 여부를 결정하는 것이 안전하다.
- JSON 대 JSON 관계 비교는 한 문서도 2단계를 함께 통과하지 못해 아직 실행되지 않았다. 따라서 두 OCR의 구조화 관계가 일치하지 않아서 0건이 된 것은 아니다.

### 7.8 후속 결론

- OCR extract와 구조화 API 호출 자체는 106문서·212 lane 모두 완료됐다.
- 정규화는 212/212 lane에서 완료됐고 추가 API 비용은 없다.
- 그러나 현재 구조화 출력은 grounding 검증을 통과한 문서가 0개이므로 채택하거나 인덱싱할 수 없다.
- 주요 회귀는 빈 `target`·불완전 fact와, 제목·주변 문맥에서 가져온 값을 단일 evidence quote에 연결하지 못한 문제다.
- 구조화 비용은 확인 가능한 최소 `$13.528108`, 관측 실행시간은 재시도 포함 약 23시간 29분이다. 품질 guardrail을 통과하지 못했으므로 비용과 시간이 들었다는 이유만으로 현재 결과를 채택하지 않는다.
- 다음 단계는 212개를 바로 재호출하는 것이 아니다. 대표 오류와 7개 차단 문서에서 소수 표본을 선정해 프롬프트·스키마·검증 규칙의 모순을 먼저 수정하고, 외부 호출 없는 저장 결과 분석과 소규모 재구조화 시험을 거쳐야 한다.

| 자체 OCR grounding 통과 | 10 lane | **0/10** | 필드 연결·ignore 규칙에서 모두 중단 |
| 문서 자동 통과 | 5문서 | **0/5** | 두 lane 모두 통과한 문서 없음 |
| 검토 필요 | 5문서 | **5/5** | 전수 재호출 중단 |

| canonical JSON | 5문서 | **0개** | 인덱싱 불가 |

**지표 설명**

- `evidence line ID 유효성`은 fact와 카드 identity가 참조한 줄 ID가 실제 같은 OCR 원문에 존재하고 중복되지 않는지 본다. 예를 들어 `편의점 10% 할인` fact가 `P0002-L0014`를 가리키면 그 ID가 해당 OCR의 실제 줄이어야 한다. 유효 ID는 높을수록 좋지만, ID가 존재한다는 사실만으로 JSON의 해석까지 옳다고 보장하지는 않는다.
- `자체 OCR grounding 통과`는 JSON의 카드명·대상·조건·수치·한도·예외와 누락 처리 모두가 **각자의 OCR**에 연결된 lane 비율이다. 예를 들어 Luna OCR로 만든 JSON은 Luna OCR만으로 검사한다. 높을수록 좋고, fact 하나라도 규칙을 위반하면 해당 lane 전체가 통과하지 않는다. 현재 규칙은 한 필드 전체가 인용문 안에 연속 문자열로 있어야 해 표와 여러 줄을 합친 정상 관계도 실패시킬 수 있다.
- `문서 자동 통과`는 Luna와 Upstage 두 lane이 모두 자체 검증을 통과한 문서 비율이다. 한 lane만 통과해도 사람 검토로 보낸다. 카드 혜택 누락을 줄이는 보수적 기준이지만, lane별 작은 형식 차이가 누적되면 문서 통과율이 지나치게 낮아질 수 있다.

`ignored_risky_lines` 계약에도 별도 불일치가 있었다. 필드 연결 검사를 진단 목적으로 건너뛰면 10개 lane 모두 ignore 검사에서 다시 멈췄다. 모델이 위험 키워드가 없는 일반 표 머리글·안내 줄까지 ignore 목록에 넣은 경우가 있고, 반대로 `포인트 메뉴 참고` 같은 비혜택 안내가 넓은 `포인트` 정규식에 걸린 경우도 있었다. 즉 line ID 자체는 정상이나, **정규화된 관계 필드와 원문 근거를 연결하는 방법 및 비혜택 안내 분류 규칙은 아직 일치하지 않는다.**

### 9.4 원인과 로컬 테스트의 누락

API 오류는 여섯 요청에서 동일했다: `structure_schema_version`의 schema에 `type`이 없다는 `invalid_json_schema` 오류다. 현재 `ocr.py`는 이 필드를 `{"const": STRUCTURE_SCHEMA_VERSION}`으로만 선언한다. API가 요구하는 문자열 타입 선언이 빠졌다. 이는 OCR 내용 오류나 자체 검증기의 과잉 차단이 아니라 **외부 API 요청 스키마 구현 오류**다.

기존 `test_schema_is_strict_and_all_object_properties_required`는 object의 필수 필드와 `additionalProperties`를 검사하지만, `const`만 있는 필드의 타입 누락은 검사하지 않았다. 따라서 이전 104개 로컬 테스트 통과는 실제 API 수락을 보장하지 않았다. 이번 실행은 그 누락을 발견했으며, v6가 실제 구조화·검증까지 동작한다는 확인은 아직 끝나지 않았다.

또한 production structurer는 예외 전체를 `retryable=True`로 분류하고 staged 실행은 다음 lane을 계속 처리해 동일한 스키마 오류가 여섯 번 반복됐다. 이번에는 SDK 재시도를 껐으므로 각 입력을 재전송하지는 않았다. 후속 수정에서는 잘못된 스키마·인증·잔액 등 공통 실행 오류를 개별 문서 품질 문제와 구분하고, 명백한 공통 오류 발생 시 나머지 요청을 중단하는 정책을 확인해야 한다.

### 10.3 원문 대조로 확인한 핵심 문제

**A. 제목과 본문의 같은 표현을 서로 다른 혜택으로 세는 검증 규칙**

BC Luna의 첫 항목은 다음 원문을 묶었다.

```text
청구할인 서비스
매일 할인 7%
점심 식사
전국 모든 식당 (오전 11시~오후 2시)
※ 1만원 이상 결제건에 한함
※ 일반 음식 업종(식당 및 레스토랑)에 한하며, 호프, 주점 등 주류 업종 제외
```

JSON에는 점심 식사·식당, 7%, 이용 시간·1만원 조건·주류 업종 제외가 들어 있다. 그런데 검증기는 제목의 `청구할인 서비스`와 본문의 `매일 할인 7%`를 별도 혜택 후보 줄로 세어 거절했다. 이 최초 실패는 7%가 1%로 바뀌어서가 아니라, 하나의 혜택에 속한 제목 반복을 처리하는 규칙 문제다. 해당 fact의 다른 필드·좌표·조건까지 모두 옳다고 보증하는 결론은 아니다.

**B. 표 위의 공통 조건을 함께 보존하면 표 범위 규칙과 충돌**

하나 Luna의 첫 항목은 표에서 `국내외 전 가맹점 / 1.0% / 한도 없음`을 가져오고, 표 위의 `지난달 실적과 관계없이 서비스 제공`을 condition에 연결했다. 그러나 현재 `table_row` 검증은 머리글 한 줄과 데이터 한 줄만 허용한다. 공통 조건 줄을 더 포함해 `table scope does not match header and row`가 됐다. 이 최초 실패는 표의 1.0%가 잘못됐다는 판정이 아니라, 공통 조건을 연결하는 모델 출력과 허용 범위의 충돌이다. 다른 표에서 실제로 관계를 잘못 합친 경우까지 모두 허용하자는 뜻은 아니다.

**C. 모델이 문구는 복사했지만 글자 위치를 잘못 계산**

KB Upstage의 원문에 `신개념 핀테크 서비스`가 실제로 존재하고 JSON의 fragment도 그 문구다. 하지만 모델이 지정한 `[42,53)` 위치를 원문에서 자르면 ` 신개념 핀테크 서비`가 되어 검사에 실패했다. BC Upstage에서는 원문 표의 `2,500원` 문구는 맞지만 지정한 위치를 자르면 ` | 2,5`가 되는 경우도 있었다. 이는 원문 위치 메타데이터 오류이며, 금액 자체를 없는 값으로 만들었다고 바로 단정할 수 없다. 원문 연결을 증명해야 하므로 잘못된 좌표를 무조건 통과시키는 것도 안전하지 않다.

6개 JSON의 795개 field fragment를 원문 줄과 독립적으로 대조한 결과, 지정 위치와 문구가 다른 fragment는 144개였다. 그중 143개는 문구 자체가 같은 원문 줄의 다른 위치에 그대로 존재했다. 나머지 1개는 `가족카드 이용으로 ...`를 `가족카드는 이용으로 ...`로 복사한 차이였다. 이 수치는 **문자 위치 검사의 진단값**이고 관계 정확도나 숫자 오류율이 아니다. 반복 금액이 같은 줄에 둘 이상 있으면 단순 첫 문자열 검색으로 위치를 보정해서는 안 된다.

- 채택·보류: 타입 선언 수정은 유지한다. 검증 규칙 완화·프롬프트 변경·좌표 자동 보정은 아직 구현하지 않았다. canonical 승인·청킹·인덱싱·106개 확대는 하지 않는다.
- 자원: 약 51분 33초, 기존 단가 적용 약 $0.511. 동일 3문서 과거 v5보다 계산 비용 약 27.7% 증가; 실제 청구액과 과거 비교 시간은 미측정이다.
- 권장 다음 확인: 저장된 결과로 제목/공통 조건의 안전한 범위 연결과 원문 근거 위치 확인 방식을 먼저 검토한다. 위치가 유일한 정확한 문구는 로컬에서 좌표를 확인할 여지가 있지만, 동일 금액이 반복되는 표 등은 열·역할 확인 없이 임의로 보정하지 않는다. 의미·수치·조건 불일치는 계속 사람 검토 대상으로 둔다.
- 승인 경계: 다음 변경은 방향 확인 후 진행한다. 추가 API 호출·106개 처리는 별도 승인 전 실행하지 않는다. 후속 실행은 사용자 지시에 따라 노트북이 아닌 운영 명령을 사용한다.
