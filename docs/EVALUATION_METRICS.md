# 평가 지표 정의

## v16 역할별 값 묶음 비교

- **Value bundle match — 역할 묶음 값 일치:** 각 혜택의 대상·동작·수치·단위를 핵심 묶음으로, 조건·한도·횟수·기간·예외·제목 잔여 정보를 별도 묶음으로 비교한다. 분모는 해당 묶음의 전체 검사 건수이며 미검사도 별도로 표시한다. 빈 필드 일치가 포함되므로 정확도·실제 관계 통과율이 아니다. 예: `전월 실적 30만원 이상`과 `300000원 이상 전월 실적`은 인식 가능한 같은 조건 원자이며, `30만원 초과`는 다르다. 미지원 표현은 잔여 문구를 보존하므로 의미가 같아도 미통과할 수 있다.
- **Role bundle equivalent — 역할 묶음 관계 일치:** `role_bundle_equivalent`는 같은 fact 안의 핵심·종속·제목 잔여 묶음이 모두 같은 경우다. JSON 배열 순서는 무관하지만 서로 다른 혜택의 조건을 교환하면 다르다. 예: 편의점10%에 붙은 전월30만원 조건을 통신비5%에 붙이면 다른 관계다. 원문 연결 확인 전의 JSON 동등성으로 단독 승인을 의미하지 않는다.
- **Title residual — 제목의 비중복 잔여:** 같은 fact의 핵심 필드에 보존된 중복 내용만 비교 제목에서 제외한다. 예: 제목의 1%가 value=1/unit=%와 중복이면 한 번만 비교하지만, 별도 '온라인 전용' 내용은 보존한다. OCR 검증에서 생략한 수치의 실제 위치 소유권을 별도로 검사한다. 모든 제목을 무시하는 방식이 아니다.
- **해석과 방향:** 묶음 값 일치와 원문 관계 입증은 다르다. 일치 수가 높아도 관계 미입증이면 PDF는 자동 승인하지 않는다. 진단 건수는 같은 혜택에 중복될 수 있다. 전체 의미를 확인하는 정답셋이 없으므로 오탐률·미탐률은 미측정이다.

## PDF별 1·2·3 검증 요약 (v15 기준, v16 위 항목 보완)

- **Document pass — 최종 PDF 통과:** 분모는 PDF 106개다. ① JSON 관계 전체 일치와 ② 두 제공자의 자체 OCR 근거 검증이 모두 통과해야 한다. 예: 편의점·10%·전월 30만원이 두 JSON에서 같고 각 OCR에도 올바르게 연결돼야 한다. 높을수록 자동 확인 범위가 넓지만 동일 오류를 공유할 수 있으므로 정답률은 아니다.
- **JSON comparison — ① JSON끼리 비교:** 분모는 106쌍이다. 배열 순서가 아닌 전체 관계와 identity를 비교한다. 확인된 연속 목록 표식만 제외한다. 자체 OCR 근거가 미확정이어도 이 비교는 실행하지만 ① 통과만으로 PDF를 승인하지 않는다.
- **Own OCR grounding — ② 자체 OCR 검증:** JSON 단위 분모는 212개이며, PDF 단위 분모 106개에서는 양쪽 모두 통과해야 한다. 예: 양쪽 JSON에 10%가 있어도 한쪽 원문은 5%라면 최종 미통과다. 관계 미입증과 실제 오류는 다르다. 높을수록 검증 범위가 넓으나 엄격한 구조 규칙 때문에 참인 항목도 검토로 남을 수 있다.
- **OCR text difference — ③ OCR 보조 비교:** 분모는 106쌍이다. 텍스트 차이만으로 PDF를 차단하지 않는다. 편의점 10%를 표와 문장으로 각각 표현해도 차이가 날 수 있다. 적을수록 유사하지만 정확성을 보증하지 않는다.
- **Match mode — 혜택 대응 방식:** 비율이 아닌 대응 항목 발생 건수다. `exact_or_list_format_equivalent`는 전체 관계 일치, `paired_for_review`는 대상·동작이 같은 양방향 유일 후보를 검토용으로만 연결, `ambiguous`는 여러 후보, `unmatched`는 대응 확인 불가다. 예: 편의점 5%와 10%는 검토용으로 대응할 수 있지만 일치가 아니다. 미대응 항목은 양쪽이 각각 집계되므로 대응 건수 합계를 혜택 수나 정확도로 해석하지 않는다.
- **Location verified — 인용 위치 확인:** 원문에서 fragment의 문자 위치를 해소했는지 나타내는 상태이며 비율 지표가 아니다. 예: 3쪽 8번째 줄의 10% 위치를 찾았다는 뜻이지 그 숫자가 편의점 혜택이라는 보증은 아니다. 미확정이면 선언된 범위만 표시하고 정확한 오류 위치로 주장하지 않는다.
- **검토 사유 묶음:** 같은 제공자 안에서 검사·필드·사유가 같은 진단을 묶어 모든 해당 항목 번호를 표시한다. 하나의 혜택이 여러 묶음에 포함될 수 있다. HTML에는 대표 인용을 미리 보여주며 모든 개별 값·위치는 연결된 `validation_summary.json`을 따른다. 이 묶음 수는 실제 오답 수가 아니다.

## 전수 검증의 독립 진단 건수

- **계산 대상과 분모:** 전체 제공자별 JSON의 진단 항목 발생 건수이며 비율 분모는 없다. 문서·JSON·fact·필드·fragment·원문 줄의 단위를 섞지 않는다. 여러 검사에 같은 문제가 중복될 수 있다.
- **Source match — 지정 원문 조각 일치:** 원문 fragment와 JSON 필드를 공통 정규화 후 비교한다. 30만원과 300000원은 일치할 수 있다. 빈 필드끼리 일치도 포함하므로 정확도나 혜택 관계 통과율로 사용하지 않는다. 이 값이 높다고 문서를 승인하지 않는다.
- **Review — 확인 필요 / Not checked — 미검사:** 위치를 확인하지 못하거나 지정 조각과 값이 다르면 확인 필요, 필수 원문 등 선행 자료가 없어 비교하지 못하면 미검사다. 예: 대상 근거가 없어도 할인율 10%와 5%는 별도 비교하며, 둘 중 하나라도 불명확하면 부분 일치로 승인하지 않는다. 낮을수록 확인 부담은 적지만 오류를 놓쳐 감소한 것은 개선이 아니다.
- **Critical content mismatch — 중요 값 차이 표시:** 숫자·비교 연산자·값/단위 차이로 표시한 진단 발생 건수다. 예: 원문 전월 30만원과 JSON 50만원. 목록 번호·제목의 숫자·필드 재배치도 포함할 수 있어 실제 혜택 오답 수로 단정하지 않는다.
- **Unclaimed source line — 미참조 원문 줄:** fact·identity·제외 목록에 선언되지 않은 중요 키워드 포함 줄 수다. 예: 통신비 10% 할인 줄이 모든 근거 목록에서 빠짐. 제목·일반 설명도 잡힐 수 있으며, 선언되어 있다는 사실만으로 근거가 올바르게 연결됐음을 보증하지 않는다.
- **통과 기준과 방향:** 위 진단 건수는 독립적인 자동 승인 기준이나 높음/낮음 목표가 아니다. 기존 자체 근거·관계·전체 포함 검사를 모두 만족해야 문서를 승인한다. 미검사는 통과로 바꾸지 않는다.

### 전체 OCR/JSON 일치 건수 — 승인 전 보조 진단

- **대상·분모:** 페이지 수·전체 정규화 텍스트·JSON 관계 키 전체 일치는 전체 비교 문서 수가 분모다. 숫자 집합 차이 페이지 수는 전체 비교 페이지 수가 분모다. 자체 근거 검증에 실패한 JSON도 포함하므로 아래 Relation match의 승인 후 분모와 구분한다.
- **방향·통과:** 일치 수는 높을수록, 숫자 집합 차이는 낮을수록 두 결과가 비슷하다. 단독 통과 기준은 아니다.
- **예시:** 같은 편의점 10% 관계가 두 JSON에서 같은 키로 나오면 일치한다. OCR에서 10과 5를 읽으면 숫자 집합 차이가 생길 수 있다.
- **한계:** 두 OCR이 같은 오류를 만들 수도 있고, 30만원/300000원 또는 목록 번호·표현·필드 분할 차이 때문에 달라질 수도 있다. 숫자 집합은 횟수·단위·혜택 연결의 정확성을 보증하지 않는다.

## OCR 진단 지표

### Token Jaccard — 단어 집합 겹침 비율

- **계산 대상과 분모:** 같은 페이지의 Luna 단어 집합과 Upstage 단어 집합의 합집합 크기를 분모로 사용하고, 교집합 크기를 나눈다. 한 문서 안에서는 페이지별 값을 평균하고, 전수 비교에서는 다시 비교 가능한 문서들의 값을 평균하는 document-macro 방식을 사용한다.
- **방향:** 높을수록 두 OCR 결과가 비슷하다.
- **통과 기준:** 단독 통과 기준으로 사용하지 않는다. OCR 차이를 찾는 진단 지표다.
- **예시:** 양쪽 모두 `편의점 10% 할인`을 읽으면 해당 단어가 겹쳐 값이 높아진다.
- **한계:** 둘 다 같은 글자를 잘못 읽어도 높을 수 있고, 표의 읽기 순서나 Markdown 표현 차이만으로 낮아질 수 있다.

### Upstage 숫자 기준 Luna 숫자 재현율 — 숫자 일치 비율

- **계산 대상과 분모:** Upstage가 읽은 서로 다른 숫자 개수를 분모로 하고, 그중 Luna에도 있는 숫자 개수를 분자로 사용한다.
- **방향:** 높을수록 Upstage의 숫자를 Luna도 많이 읽었다.
- **통과 기준:** 단독 통과 기준으로 사용하지 않는다. 숫자 차이가 큰 문서를 검수 대상으로 찾는 지표다.
- **예시:** Upstage가 `전월 30만원, 월 1만원`을 읽고 Luna도 `30`, `1`을 읽으면 100%다.
- **한계:** Upstage가 휴대전화 화면, 마스킹 카드번호 또는 장식 숫자를 잘못 읽으면 Luna가 정확해도 낮아질 수 있다. Upstage는 gold가 아니다.

## 구조화·근거 검증 지표

### Grounding pass — 자체 OCR 근거 연결 통과율

- **계산 대상과 분모:** 구조화 대상 문서 수를 분모로 하고, Luna와 Upstage 두 lane 모두에서 identity·fact·evidence quote·span disposition 검증을 전부 통과한 문서 수를 분자로 사용한다.
- **방향:** 높을수록 좋다.
- **통과 기준:** 문서의 두 lane이 모두 자기 OCR 원문에 근거해야 해당 문서를 통과로 센다. 하나의 필드나 줄 분류라도 위반하면 통과하지 않는다.
- **예시:** `편의점 10% 할인` fact의 target, value, unit과 인용문이 같은 lane OCR에서 확인되고 해당 OCR 줄도 fact로 분류되면 근거 연결 조건을 만족한다.
- **한계:** OCR과 의미가 맞더라도 target이 바로 위 제목에만 있고 단일 인용문 안에는 없으면 현재의 엄격한 문자 연결 규칙에서 실패할 수 있다. 따라서 실패가 곧 사실 오류를 뜻하지는 않는다.

### Relation match — 두 구조화 JSON의 fact 관계 일치율

- **계산 대상과 분모:** Grounding pass를 통과한 문서를 분모로 하고, Luna와 Upstage의 identity와 전체 fact tuple이 모두 일치한 문서를 분자로 사용한다.
- **방향:** 높을수록 좋다.
- **통과 기준:** 두 lane의 카드 identity와 모든 `target·condition·value·unit·cap·frequency·period·exceptions` 관계가 같아야 통과한다.
- **예시:** 양쪽 JSON이 모두 `편의점 / 전월 30만원 / 10 / % / 월 5천원` 관계를 만들면 해당 fact는 일치한다.
- **한계:** 두 OCR과 두 구조화 모델이 같은 오류를 만들면 일치율은 높아도 정확하지 않을 수 있다. 반대로 표현만 다르고 의미는 같은 fact도 exact tuple 비교에서는 불일치할 수 있다. 분모가 0이면 0%가 아니라 `미측정`으로 보고한다.

### Automatic canonicalization — 자동 canonical JSON 생성률

- **계산 대상과 분모:** 전체 구조화 대상 문서 수를 분모로 하고, Grounding pass와 Relation match를 모두 통과해 자동 canonical JSON이 생성된 문서 수를 분자로 사용한다.
- **방향:** 높을수록 좋다.
- **통과 기준:** 두 lane의 근거 연결과 관계 일치를 모두 통과해야 한다.
- **예시:** Luna와 Upstage가 같은 카드명과 편의점 할인 관계를 각자 자기 OCR 근거로 뒷받침하면 두 근거를 가진 canonical fact를 생성한다.
- **한계:** 자동 생성률이 낮다고 OCR 품질이 반드시 낮은 것은 아니다. 구조화 프롬프트와 검증 규칙이 지나치게 엄격하거나 서로 맞지 않아도 낮아질 수 있다.
