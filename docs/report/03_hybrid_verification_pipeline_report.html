왜 이 테스트를 했나

단일 OCR 결과를 바로 쓰지 않고 엔진 대조와 검토 경로를 결합할 필요를 확인하려 했다.

이 테스트로 무엇을 확인하려 했나

자동 통과·재시도·검토로 나누는 초기 검증 흐름이 위험한 수치 오류를 줄일 수 있는지 살폈다.

혼합형 OCR 검증 파이프라인 결과 보고서

confidence 임계값 라우팅 + 위험도 계층화 + 멀티엔진 교차검증을 결합한 파이프라인을 실제로 구현·실행한 결과. 신용카드 상품설명서 OCR 파이프라인에서 "잘못된 정보가 검증 없이 사용자에게 전달되는" 리스크를 어떻게 줄일지에 대한 논의를 코드로 검증했다. 이 보고서는 v2(교차검증 상시 적용) 기준으로 갱신됐고, v1(confidence 지름길 포함) 시점의 발견 사항은 3절에 요약으로 남겨뒀다.

범위: 기존 3엔진 비교(03_ocr_engine_comparison.ipynb)와 동일한 10개 카드사, 10페이지, 43개 필드 표본을 재사용했다. 노트북은 notebooks/05_hybrid_verification_pipeline.ipynb이며 전 과정이 실행 완료된 상태로 저장되어 있다.

1. 배경 및 설계 조정 사항

애초 논의에서는 "Upstage 같은 Document AI는 필드별 confidence를 제공한다"는 일반론을 전제로 설계를 시작했다. 그러나 실제 이 프로젝트가 받은 Upstage Document Parse API 응답(notebooks/data/03_ocr_engine_comparison/upstage_raw/*.json)을 직접 열어본 결과, elements에는 id/page/category/content/coordinates만 있고 confidence 관련 필드는 전혀 없었다 (ocr 키는 단순 불리언 플래그였다). 이 발견에 따라 설계를 다음과 같이 조정했다.

  • Upstage는 confidence 없는 엔진으로 취급한다. Upstage의 원문(markdown 또는 html)을 별도 LLM 호출로 구조화하는 어댑터 방식을 썼다. 필드값만 주고 confidence는 주지 않는다.
  • GPT Vision의 confidence는 self-reported(언어모델이 말로 지어내서 보고하는 확신도)다. 모델 내부의 진짜 토큰 확률이 아니라 "0~1 사이로 스스로 평가해서 답하라"고 프롬프트로 지시해서 받은 값이며, 실제 정답률과 상관관계가 약한 신호로 알려져 있다.

2. 정답셋 재검증

기존 03_manual_field_gold.json은 다른 AI 세션이 작성한 것이어서 사용자가 신뢰도에 우려를 제기했다. Claude가 동일한 10장의 렌더링 페이지 이미지(03/rendered_pages/*.png)를 직접 읽고 43개 필드값을 재검증했다. 결과는 05/manual_field_gold_claude_verified.json이다.

재검증 결과: 43개 필드 중 42개는 원문과 정확히 일치했다. 1개 필드만 캡처된 페이지 이미지 내에서 명시적 근거를 찾지 못해 낮은 신뢰도로 별도 표시했다.
  • woori/minimum_transaction: 렌더링된 페이지 이미지 안에서 '2만원 이상'이라는 건당 최소 결제금액 조건의 명시적 근거 문구를 찾지 못함. 이전 라벨값을 그대로 유지하되 낮은 신뢰도로 표시함. 원본 PDF의 다른 페이지(예: 유의사항 상세 페이지)에 있을 가능성이 있으나 확인하지 않음.

3. v1(1차 버전)에서 있었던 테스트와 발견된 문제 이력 요약

v1 설계: 고위험 필드는 항상 GPT Vision-Upstage 교차검증, 저위험 필드는 GPT Vision의 self-reported confidence가 0.8 이상이면 Upstage 대조 없이 단일 엔진만으로 자동통과시켰다 (비용 절감 목적).

v1 실행 결과(첫 실행 기준): 전체 43개 필드 중 자동통과율 62.79%, 자동통과분 정확도 96.3%, GPT Vision이 확신했지만 틀린 사례 7건.

발견된 문제: lotte / excluded_loan 필드에서 GPT Vision이 confidence 0.95로 확신하며 오답("장기카드대출(카드론)", 정답은 "단기카드대출(현금서비스)")을 냈는데, 이 필드가 저위험으로 분류되어 있어 confidence만 보고 Upstage 대조 없이 그대로 자동통과됐다. 원문에는 두 항목이 나란히 나열돼 있었고, GPT가 confidence 0.95로 확신하며 바로 옆의 다른 항목을 골라 틀린 것이었다.

조치: 이 발견을 근거로 "위험도·confidence와 무관하게 항상 GPT Vision과 Upstage가 일치해야만 자동통과"하는 v2로 라우팅 로직을 수정했다. 근거: 이 표본에서 고위험 필드가 43개 중 37개(86%)라 confidence 지름길로 아낄 수 있는 비용 자체가 애초에 작았고, 반면 안전성 손실 사례는 실제로 확인됐기 때문이다.

4. v2 파이프라인 설계

필드명을 규칙기반 키워드(rate, limit, fee, spend, cashback, transaction, date, center, time)로 위험도를 나누되, 위험도와 무관하게 모든 필드는 GPT Vision과 Upstage 두 엔진의 값이 일치해야만 자동통과한다. confidence는 더 이상 통과 여부를 결정하지 않고 진단용 참고 데이터로만 기록한다.

정확한 구현: notebooks/05_hybrid_verification_pipeline.ipynb 셀 7(라우팅 로직 v2) 참고.

6. v1 → v2 정책 비교, 그리고 비결정성에 대한 주의

중요한 주의사항: GPT Vision은 결정론적이지 않다. v1과 v2는 서로 다른 시점에 API를 재호출해서 얻은 결과라, 순수하게 "정책 차이"만 비교한 게 아니라 "모델의 실행별 무작위성"도 섞여 있다. 그래서 v1 실행(위 3절)과 v2 실행(5절)의 전체 지표를 직접 비교해 "정책 변경 효과"라고 결론 내리는 것은 부정확하다.

대신 같은 v2 실행 데이터 안에서 v1이었다면 어떻게 됐을지를 재계산해서 비교했다(같은 엔진 출력값 기준이라 이 비교는 공정하다). 그 결과 정책 차이로 최종 통과 여부가 달라진 필드는 2건이다.

11. 한계 및 다음 단계

  1. 표본 규모: 10페이지, 43개 필드는 스모크 테스트 규모다. 통계적으로 확정적인 결론(예: 임계값 최적값)을 내리기엔 작다.
  2. 모델 비결정성: GPT Vision을 재호출하면 같은 페이지에서도 다른 답이 나올 수 있다는 것을 이번 v1→v2 재실행에서 직접 확인했다 (6절). 향후 비교 실험은 가능하면 동일 실행 내에서 정책만 바꿔 비교하거나, 여러 번 반복 실행한 분포로 판단해야 한다.
  3. 상관 오류는 구조적 한계: 7절에서 확인했듯, 두 엔진이 같은 표/같은 모호한 필드명을 두고 같은 실수를 하면 교차검증으로 못 잡는다. 이건 엔진을 더 늘리는 것만으로는 완전히 해결되지 않으며, 필드 정의를 더 명확히 하거나 표 구조 자체를 별도로 검증하는 장치가 필요하다.
  4. 값 비교 로직 개선 필요: 나열형 필드(여러 항목이 쉼표로 나열된 경우)에서 부분문자열 포함 기반 비교가 오탐(false agree)을 낼 수 있다. 정확한 항목 단위 비교로 개선이 필요하다.
  5. GPT Vision 프롬프트 개선: 이번 프롬프트는 필드명만 bare하게 제시했다. 실제 프로덕션 파이프라인의 extract_02_structure_json.py처럼 각 필드가 무엇을 의미하는지 상세히 설명하면, NH/hana 사례의 누락이나 woori 사례의 열 혼동이 줄어들 가능성이 있다 (확인 안 됨, 추측).
  6. Upstage confidence 부재 재확인 필요: 이번에 확인한 것은 document-parse-260128 모델 응답 1건 기준이다. 다른 엔드포인트/파라미터 조합에서는 confidence가 제공될 수도 있으므로 운영 전환 시 공식 문서로 재확인이 필요하다 (확실하지 않음).
