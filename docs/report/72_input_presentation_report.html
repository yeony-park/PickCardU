1. 목적과 비교 조건

구조화 DB의 전체 행·추적 자료를 서버에 보존하면서, LLM에는 필요한 업무정보를 간단한 JSON 또는 읽기 쉬운 텍스트로 전달해도 되는지 확인했다. 새 검색은 실행하지 않았다. 70번 수정 순차의 검색 r2에서 카드·순위·비정형 본문·추가 구조화 행·근거 ID를 고정했다. benefit과 parent-child의 기존 최선 검색 프로필도 유지했다.

  1. A — 전체 필드 JSON: 원래 canonical 행의 업무값·파생 설명·출처 연결을 유지하고 긴 카드·사실·경로 ID만 C/F/P로 치환했다.
  2. B — 간단한 JSON: 같은 행의 비어 있지 않은 업무 10필드와 해석 상태 5개를 전달했다. 카드명·발급사는 공통 카드목록으로 묶었다.
  3. C — 간결한 텍스트: B와 같은 업무값·상태를 한국어 라벨과 원래 문자열로 전달했다.

세 조건 모두 같은 구조화 근거를 추가한다. 원질문과 기존 비정형 본문도 그대로 전달한다. 이 변환은 검색이 끝난 뒤 LLM 요청을 조립할 때 적용하며, 임베딩 질의나 카드 검색 범위를 바꾸지 않는다.

비교의 정확한 범위: A/B는 파생 판단 사유·질문 조건 연결 등도 함께 제거하는 비교다. 추적 해시 삭제만의 효과로 해석할 수 없다. B/C는 업무값과 행·근거 순서가 같지만, B의 영문 키 정렬과 C의 한국어 라벨·대상 우선 배치도 다르다. JSON 문장부호만 바꾼 실험은 아니다. A도 새 공통 카드목록·별칭·안내 지시문을 사용하므로 이전 운영 입력 그대로의 대조군이 아니다.

질문은 C01·C10·C12·C13·C14·C16·C17·C18이다. 70~71번에서 사용했던 질문을 골랐으므로 개발 비교이며 독립 확인셋이 아니다. 반복마다 새 답변을 생성했고, ABC → BCA → CAB 순서를 순환했다. 입력 캐시 토큰은 재사용됐지만 완성 답변을 다른 반복에 재사용하지 않았다.

2. DB 컬럼 중 무엇을 전달했는가

아래는 물리 컬럼과 LLM용 조립 필드를 구분한 표다. “전달”은 모델이 판단할 수 있도록 제공한다는 뜻이며, 사용자 화면에 모든 조건을 반드시 출력하라는 뜻은 아니다. 해당 조건을 묻지 않았다는 이유만으로 설명 생략을 실패 처리하지 않았다.

구분실제 DB 컬럼 또는 조립 경로B/C의 전달 방식이유
카드 식별 · 전달documents.card_name, issuer_name공통 카드목록의 카드명·발급사와 짧은 card_ref어느 카드의 혜택인지 연결한다. 선택된 13카드의 검색 메타데이터와 DB 값이 모두 일치했다.
혜택 업무값 · 전달facts.target_raw, action_raw, benefit_type_raw, value_raw, unit_raw대상·혜택 방식·분류·값·단위의 원문동물병원과 멤버십의 요율처럼 서로 다른 혜택의 숫자를 합치지 않는다.
적용 업무값 · 전달condition_raw, cap_raw, period_raw, frequency_raw, exceptions_raw같은 행의 비어 있지 않은 원문을 그대로 유지실적·한도·기간·횟수·제외를 해당 혜택에 연결한다. 지급할인액과 할인 대상 결제금액 상한은 구분해야 한다.
해석 상태 · 이번 비교에서 보존action_status, percent_state, spend_state, cap_state와 derived_json.cap_period_state상태 5개unknown을 0원·무제한·조건 없음으로 바꾸지 않는다. 상태 자체가 원문의 적용 관계를 확정하지는 않는다.
서버 보관 · B/C에서 제외document_id, fact_id, ordinal, provider, source_*sha256, normalized_json_sha256, source_relative_path, page_count, fact_count, raw_json짧은 ID의 역변환 표와 원본 행은 서버 sidecar에 보존원문 추적·재검증·장애 분석에 쓰인다. 긴 경로와 해시 전체를 매번 LLM에 보낼 필요와 구분했다.
중복 수치·추출 자료 · B/C에서 제외action_kind, percent, spend_threshold_krw, spend_operator, cap_krw, cap_period 및 나머지 derived_json업무 원문값은 유지하고 중복 정규화 값·판단 사유는 제외이번 A/B는 이 제거 효과도 포함한다. 파생 설명이 업무 판단을 돕는 경우까지 무조건 불필요하다고 결론 내릴 수 없다.
별도 조립 자료 · 서버 보관field_evidence, relation_scope, requirement_links — canonical JSON의 조립 필드이며 각각 독립 SQL 컬럼이라는 뜻은 아님전체 자료는 sidecar에 보존하고 evidence_id / fact_ref로 연결원문 위치와 실제 적용 관계를 혼동하지 않는다. 적용 관계는 업무 원문 또는 같은 카드의 기존 본문에 남아 있어야 한다.

빈 업무값 생략은 “그 행에 미기록”이라는 뜻이다. 신규 실적 유예를 정규 무실적으로 바꾸지 않으며, 선택서비스 변경 횟수를 할인 사용 횟수로 바꾸지 않는다. 원래 비정형 본문 안의 카드명 반복은 수정하지 않았다. 전체 입력에서 카드명이 단 한 번만 나온다는 보장은 아니다.

metadata.key / value_json의 빌드 설명과 target_aliases.alias_group / alias / alias_normalized의 대상 확장 규칙도 서버 보관 범위다. 이번 답변 입력에는 테이블 전체를 전달하지 않았다. 검색 규칙과 사용자에게 설명할 혜택 사실은 구분한다. 전체 테이블 정의는 DB 명세서에서 확인한다.
