평가 범위와 판정 방법

수기 structured gold와 critical fact v2가 정확하다는 전제에서 gold 값 → 해당 페이지 OCR 문맥 → 공통 스키마 JSON 값을 비교했다. OCR 문맥이 이미 틀리면 OCR 단계, OCR에는 정답 관계가 있으나 JSON 값이 틀리면 구조화 단계로 귀속했다. 분류는 카드·항목별 명시적 감사 규칙이며, 실행할 때마다 해당 OCR 문구가 실제로 존재하거나 특정 혜택 문맥에서 누락됐는지 검증식으로 확인한다.

  • OCR 오류: 숫자를 다른 값으로 읽었거나 필요한 조건을 누락했고 JSON이 이를 그대로 따랐다.
  • JSON 오류: OCR은 맞지만 표의 행·열 연결, 필드 누락 또는 백분율 정규화에서 틀렸다.
  • 표 의미 규칙: OCR은 빈칸 또는 -를 보존했지만 gold는 이를 0원으로 해석했다. OCR 정확도와 별개인 스키마 규칙 문제다.

하나의 원인이 semantic 관계 라벨과 numeric probe에 동시에 나타날 수 있다. 따라서 아래에는 “오답 라벨 수”와 한 실행 안의 중복 원인을 묶은 “실행별 원인 발생 건”을 모두 제시한다. 같은 원인이 다른 반복 실행에서 재발하면 각각 1건으로 센다.

운영 검증 구조에 주는 의미

  1. OCR 직후에는 정답 없이도 두 엔진의 핵심 수치·문맥 불일치를 찾아 재검수 대상으로 보낼 수 있다.
  2. JSON 구조화 후에는 반드시 OCR 근거 문구와 JSON 값을 역대조한다. OCR에 맞는 값이 있는데 JSON이 다르면 재구조화하거나 규칙 기반 정규화를 적용한다.
  3. 빈칸/-를 0원으로 볼 수 있는 열은 스키마에 명시한다. 문서 종류와 열 의미를 확인하지 않고 모든 빈칸을 0으로 바꾸면 안 된다.
  4. 최종 통과는 수치만이 아니라 대상·조건·단위가 같은 관계 그룹 단위로 결정한다.
