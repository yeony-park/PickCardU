# OCR 검증·원문 청킹·검색 설정 정합성 수정

## 목적과 범위

과거 실험에서 사용한 검색 후보 구성과 현재 서비스 구현의 차이를 줄이고, OCR → JSON 변환에서 숫자가 다른 혜택에 연결되는 오류를 차단하기 위한 구현 작업이다. 검색 품질의 우열을 다시 평가하는 실험은 아니다. 두 청킹 프로필을 유지하고 기본값은 benefit으로 둔다. UI와 Luna 답변 모델·프롬프트·reasoning 설정은 변경하지 않는다.

기준 근거는 MS 브랜치의 28번 통합 holdout 후보 계약과 24번 후보 깊이 후속 실험이다. 마지막 holdout은 두 후보 모두 D20·Top3였으며 둘 다 최종 답변 통과 기준을 충족하지 못했다. 따라서 이번 설정은 **개발 구현 기준**이지 생산 품질 인증이 아니다. 과거 Python BM25 대신 SQLite FTS5를 사용하는 것은 이후 승인된 변경이다.

과거 근거 위치(MS 확인 시점 `a2367e1`): `notebooks/28_integrated_holdout_candidate_evaluation.ipynb`, `notebooks/data/28_integrated_holdout_candidate_evaluation/llm_answer_summary.json`, `notebooks/data/24_multicard_recommendation_retrieval_evaluation/followup5_summary.json`. 이 파일들은 MS의 실험 기록이며 현재 엔진 브랜치로 복사하지 않는다.

## 승인된 변경 계약

| 영역 | 구현 계약 |
|---|---|
| 데이터 준비 | extract → structure → normalize → validate 단계와 OCR 원응답·원문 보존 |
| JSON | 원문 필드와 필드별 출처·관계 범위를 보존하고 비교용 수치 정규화를 로컬에서 생성 |
| 관계 | 대상·혜택 종류·수치·단위·조건·한도·기간·예외를 함께 비교 |
| 자기 결과 검사 | 원문에 숫자가 있다는 사실뿐 아니라 해당 혜택에 연결된 수치인지 확인 |
| 독립 검사 | OCR끼리, Luna OCR↔JSON, Upstage OCR↔JSON, JSON끼리 계산은 독립; 기록·승인은 단일 수집기 |
| 승인 | source 무결성, 양쪽 자기 결과 검사, 전체 관계 비교와 누락 검사를 만족해야 승인 |
| benefit 청킹 | JSON 필드 문자열 대신 검증된 OCR 원문 구간을 본문으로 사용 |
| benefit BGE | 의미 질의만 제목·경로 보강한 개별 청크를 평가; 선정 section을 자식으로 치환하지 않음 |
| parent-child BGE | 같은 카드의 주변 근거 최대 5개를 먼저 묶고 모든 질의에 BGE 적용 |
| 검색 | BM25 Top50 + 벡터 Top50 → RRF 통합 Top50 → 프로필별 대상 필터 → D20 |
| RRF | 벡터 0.4, BM25 0.6, 상수 60; 동점은 구성 검색의 가장 높은 순위 → 청크 ID |
| 출력 | 기본 Top3 카드, Top5 선택 가능; 카드당 고유 근거 최대 5개 |
| 근거 예산 | 선정 근거가 예산을 넘으면 명시적 오류; 부분 근거를 정상 패키지로 반환하지 않음 |
| BGE 길이 | 전체 입력 최대 8,192토큰(모델의 더 작은 실제 한도 우선), parent-child 본문 최대 4,096토큰; 잘림 금지 |

benefit의 본문은 승인된 원문 line ID를 따라 읽어 원래 줄바꿈을 유지한다. section은 앞선 실제 Markdown 제목 경로로 묶으며, JSON의 target이나 본문 전체를 제목으로 만들지 않는다. 제목이 없는 곳은 페이지 번호로 표시한다. 출처 파일의 해시가 달라지면 청킹을 차단한다. 과거 평가 정답을 이용한 문단 선택은 운영 코드에 이식하지 않으므로, 과거 청크 개수·경계까지 그대로 재현했다는 뜻은 아니다.

parent-child는 BGE가 본 카드명·상위 제목·근거별 경로까지 답변 입력에 유지한다. 원래 chunk ID는 보존하되 답변용 text에 동일한 경로 라벨을 붙이며, 카드별 근거 text를 순서대로 합치면 BGE 입력 bundle과 정확히 같다. 이는 출력 근거의 표현 변경이며 저장된 OCR·청크 원문이나 답변 프롬프트를 수정하는 것이 아니다. 추가된 라벨도 답변 입력 예산 계산에 포함한다.

### 정규화와 출처의 예

위 일치 조건은 자동 승인 기준이다. 기존의 명시적 수동 검토 절차는 유지한다. 양쪽 자체 원문 검증에 성공한 관계 중 검토자가 한쪽을 선택할 때는 선택한 provider, 반대쪽의 거절 관계, 이유 및 양쪽의 정확한 출처를 모두 감사 기록으로 남긴다. 자체 grounding 실패나 오래된 스키마를 수동 선택만으로 우회할 수는 없다.

`편의점 10% 할인, 전월 실적 30만원 이상`의 원문은 유지한다. JSON 비교용 금액은 300000원으로 통일한다. `30만원 초과`, `통신비 10%`, `편의점 1%`는 같은 관계가 아니다. 두 JSON이 같은 오류를 내면 JSON끼리 일치할 수 있으므로 각 OCR과의 자기 결과 검사가 반드시 필요하다. 두 OCR이 PDF를 똑같이 잘못 읽는 경우까지 이 검사만으로 증명할 수는 없다.

원문 field와 문자 좌표는 lane artifact에 보존하고, canonical fact에는 NFKC·공백 정리와 비교용 typed 값을 사용한다. 청킹 본문은 canonical 필드를 조합하지 않고 해시가 확인된 원본 lane에서 읽는다. `300000원 = 300000.0원`, `value: 10 / unit: % = value: 10% / unit: %`도 같은 비교 키를 만들지만, 비율과 원화처럼 차원이 다른 unit은 거부한다. 임의의 동의어·의미 유사도를 근거로 자동 일치시키지는 않는다.

로컬 normalize 결과의 일부 예시(전체 schema가 아니라 설명용 발췌):

```json
{
  "condition": "전월 실적 30만원 이상",
  "value": "10",
  "unit": "%",
  "typed_normalization": {
    "condition": [{"kind": "KRW", "decimal": "300000"}],
    "value": [{"kind": "ratio", "decimal": "0.1"}],
    "condition_operators": ["gte"]
  }
}
```

`gte`는 이상(경계 포함), `ratio`는 비율이다. decimal은 부동소수점 오차를 피하도록 문자열로 저장한다. 이 비교용 값이 OCR 문장이나 외부 구조화 원응답을 덮어쓰지는 않는다.

### 검색 정규화

과거의 한국어 2·3·4글자 부분 문자열과 금액·비율·기간 검색 별칭을 복원한다. 이 처리는 검색용이며 원문을 교정하거나 정답을 판정하지 않는다. FTS5 내부 토큰 분리로 별칭이 훼손되지 않게 각 토큰을 ASCII hex로 저장하고 질의에도 같은 변환을 적용한다. 인덱스와 검색 코드의 `lexical_contract`가 다르면 로딩을 거부한다. 이 변화는 인덱스 재생성이 필요하며, 기존 인덱스를 자동 덮어쓰지 않는다. n-gram/별칭/hex 저장에 따른 크기·속도 변화는 미측정이다.

### 질의 분류

기존 선택적 BGE 정책은 유지한다. 명확한 발급사·발행사·은행 질문과 숫자·기간·횟수 질문을 규칙으로 보강한다. `30만원 쓰는데 어떤 카드가 좋아?`처럼 숫자가 포함돼도 추천을 요구하면 의미 질의로 남긴다. 규칙 테스트 통과는 실제 사용자 질의의 분류 성능 검증을 뜻하지 않는다. 애매한 표현은 후속 개발 평가가 필요하다.

## 검증과 주의점

인덱서와 서비스가 같은 검색 토큰 함수를 사용하도록 인덱서에 로컬 `pickcardu-rag==0.1.0` 의존성을 명시했다. 설치 안내는 저장소의 `packages/rag-core`와 `jobs/rag-indexer`를 함께 editable 설치하도록 수정했다. 이번 작업에서 패키지를 실제 설치하거나 공용 환경의 버전을 변경하지는 않았다. 새 코드에서 이전 토큰 형식 인덱스의 활성화·로딩은 거부되므로, 기존 인덱스 재사용을 위한 코드 롤백과 새 코드용 인덱스 재생성은 구분해야 한다.

외부 API 호출, 모델 다운로드, 실제 카드 데이터 재구조화·재임베딩·활성 인덱스 변경은 이번 로컬 검증에 포함하지 않는다. 새 스키마에 맞는 실제 Luna 생성 능력과 106개 문서 통과율은 승인된 소수 재호출 전까지 미검증이다. 과거 스키마의 저장 결과를 새 스키마 통과 사례로 간주하지 않는다.

새 구조화 스키마는 OpenAI Structured Outputs의 모든 객체 추가 속성 금지·필드 필수 지정 규칙에 맞춰 정적 검사한다. 이는 실제 API 접수·출력 품질을 대신하지 않는다. [공식 스키마 제한](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas)

자동 승인 범위는 단일 문장, 같은 페이지의 연속된 단일 혜택 블록(최대 6줄), 명확한 pipe 표의 header 1개+data row 1개로 제한한다. 빈 셀·병합 셀·알 수 없는 수치 열·모호한 관계는 검토 대상으로 남긴다. 이는 모든 문장의 의미를 이해하는 검증기가 아니라, 지원하는 구조에서 원문 숫자·단위·역할 연결을 보수적으로 확인하는 코드다. 실제 문서에서의 오탐·미탐률은 미측정이다. parent-child의 승인 scope가 생성 청크에서 확인되지 않으면 release를 차단하므로 계층 경계나 긴 근거의 처리는 실제 소수 검증에서 함께 확인해야 한다.

현재 환경에서 `python -m pytest`는 pytest 미설치로 실행되지 않았다. 패키지를 설치하지 않고 기존 unittest 기반으로 검증한다. FastAPI TestClient는 프로젝트와 무관한 최소 앱에서도 대기 후 timeout이 재현됐다. 따라서 HTTP 전송 검증과 직접 endpoint 호출 검증을 구분한다. 의존성 버전 변경은 하지 않는다.

## 검증 결과

custom `reviewer`가 수정 후 코드를 독립 검토했고, main Codex도 중요 함수와 반례를 직접 확인했다. 리뷰 중 발견한 다음 사항을 수정하고 재검토했다.

- parent-child의 BGE 입력에는 있던 제목·경로가 답변 입력에서 빠짐 → 동일 렌더링 보존 및 실제 답변 payload 재구성 일치 검사.
- 한 줄의 조건·한도 교환 → 역할 표지의 정확 문자 범위를 해당 field에 귀속.
- 표 header/row 충돌과 열 교환 → header 역할과 같은 열의 data cell을 연결.
- 동등한 금액 소수 표기·inline unit의 불일치 → 비교 키 정규화.
- `%`나 중간 `만원`, 표의 `이상` 삭제 → 원문 단위 보존, fragment 사이 비공백 생략 차단, 표 셀 전체 보존.

최종 reviewer의 정적 검토에서 Blocker/Major(완료를 막는 중대한 문제)는 없었다. 마지막 fullwidth `％`의 불필요한 거부도 수정 후 재확인했다. reviewer는 테스트를 실행하지 않았으며, 아래 실행 결과는 구현 담당자와 main Codex의 로컬 실행 결과다.

| 로컬 검증 범위 | 테스트 수 | 최종 결과 | unittest가 보고한 실행 시간 |
|---|---:|---|---:|
| 인덱서: OCR mock·구조화·정규화·검증·청킹·인덱스 | 75 | 모두 통과 | 17.474초 |
| 검색 핵심: 분류·RRF·BGE·근거 전달 | 16 | 모두 통과 | 0.010초 |
| API 인덱스: 로딩·계약·FTS 검색 | 10 | 모두 통과 | 5.790초 |
| 답변 endpoint 직접 호출: 선정 근거 보존·예산 초과 | 1 | 통과 | 0.008초 |
| API 설정 | 2 | 모두 통과 | 0.000초(출력 정밀도 미만) |

이 수는 실행한 테스트 함수 수이며 실제 질의 정답률이나 106개 문서 승인율이 아니다. 표의 시간은 최종 로컬 실행 1회의 unittest 측정값으로, Conda 시작 시간과 실제 API·GPU 처리 시간을 포함하지 않는다. 일부 묶음은 서로 독립적인 프로세스에서 실행했으므로 시간을 더해 전체 소요 시간으로 해석하지 않는다. 표준편차와 최대 메모리는 미측정이다.

재현 명령(전체 노트북 재실행이 아닌 구현 테스트):

```bash
conda run -n skn25 python -m unittest discover -s jobs/rag-indexer/tests -q
PYTHONPATH=packages/rag-core/src conda run -n skn25 python -m unittest discover -s packages/rag-core/tests -q
conda run -n skn25 python -m unittest discover -s services/rag-api/tests -p test_index.py -q
conda run -n skn25 python -m unittest discover -s services/rag-api/tests -p test_evidence_transport.py -q
conda run -n skn25 python -m unittest discover -s services/rag-api/tests -p test_config.py -q
```

수정 Python 모듈의 compile과 `git diff --check`도 통과했다. HTTP TestClient 전체 테스트와 실제 모델 품질 평가는 위 104개에 포함되지 않는다. UI·답변 프롬프트·모델 설정 파일의 diff는 없었다.

저장 5문서(run_48c89f58869e2d44)의 양쪽 normalized JSON 10개에 새 validator를 읽기 전용 적용한 결과, 이전 스키마 차단 10개·예상 밖 승인 0개였다. 전후 파일 SHA-256은 모두 동일했다. 이는 기존 OCR이 틀렸다는 평가가 아니라 이전 결과가 v6 검증을 통과한 것처럼 재사용되지 않는지 확인한 검사다.

- 수정 후에도 과거 holdout 수치를 현재 106개 서비스 파이프라인의 성능으로 인용하지 않는다.
- 로컬 검증과 독립 리뷰를 마친 뒤 새 스키마 소수 구조화 호출을 별도 승인받아 검증한다. 문제를 해결한 뒤에만 전수 처리·인덱스 생성·후속 검색 평가를 진행한다.

## 최종 요약

관계·단위·조건 누락 검증, 검증된 원문 청킹, 제목·주변 근거 보존과 검색 계약을 구현하고 관련 로컬 테스트·독립 코드 리뷰를 마쳤다. 기존 benefit 기본값과 두 후보 프로필, SQLite FTS5, Luna 답변 설정을 유지했다. 자동 의미 유사도 승인, 부분 근거의 조용한 삭제, 구 스키마의 무검증 재사용은 채택하지 않는다.

검색 품질 향상·회귀와 실제 비용·시간 개선은 아직 측정하지 않았다. 새 검증이 보수적이므로 정상 문서의 검토 비율이 높아질 가능성도 있다. **코드 구현 완료와 실제 106개 문서 처리 완료는 다르다.** 다음 단계는 기존 OCR을 보존·재사용한 소수 JSON 구조화 및 검증이며, 별도 API 승인 후 수행한다. 그 결과를 확인한 뒤 나머지 문서와 새 인덱스로 확대한다.
