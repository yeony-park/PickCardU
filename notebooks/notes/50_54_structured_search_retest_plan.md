# 50–54 구조화 검색 재실험 계획

2026-10-22 승인된 계획. 운영 코드·OCR·원본 DB·기존 색인은 읽기 전용이다. API 사용은 기존 46–49 비용을 포함해 8달러 이내이다. 이전 결과는 보존한다.

## 비교할 검색 흐름

- `S_ONLY` 구조화 단독: 조건 추출 → DB 조회 → 구조화 근거로 답변. 결과가 없으면 근거 없음. 비구조화 검색 없음.
- `U` 비구조화 단독: 원질문 → Vector + BM25 → 기존 재정렬 → 답변.
- `SEQ` 순차: 조건 추출 → DB 조회 → 카드가 있으면 해당 카드에서 원질문으로 U, 없으면 원래 허용 범위에서 U → 답변. U 경로는 한 번이다.
- `PAR` 병렬: DB 조회 결과와 독립적인 U 결과를 카드 ID로 합침 → 동일한 BGE로 근거 단위 재정렬 → 답변. `(S→U)+U`는 비교하지 않는다.

발급사·상품 범위는 모든 방식에 동일하게 적용한다. BC와 IBK는 구분한다. 오타 자동 보정은 보장하지 않는다. 커피 등 기존 별칭만 재사용하며 기차와 전기차의 잘못된 부분 문자열 일치는 제거한다.

## 순서와 통과 조건

1. **50 오프라인 수정·재현**: H01–H32와 사용자 예시 8개를 개발 질문 40개로 동결한다. 필터와 상세 설명 요청을 구분하고, H08/H11의 DB 조회 이전 복귀, 빈 AND, 같은 카드 AND, 발급사 범위, 숫자·기간·횟수 경계를 회귀 검사한다. 원본 DB/PDF 관계를 확인한다. 전체 3,403개 사실을 누락 없이 직렬화해 기존 BGE 문서 4,096/쌍 8,192 토큰 경계를 검사한다. 초과 시 유료 단계에 진입하지 않고 원인을 보고한다.
2. **51 조건 추출·범위**: 40문항 × 3회 신규 추출, 최대 120회. 1회차만 52에 사용하며 더 잘 나온 회차를 고르지 않는다. 실제 SQL·조건·일치 사실·카드 범위·복귀 사유·소요 시간을 기록한다. Vector와 BM25 모두 후보 제한 이전에 범위를 적용한다.
3. **52 네 방식 비교**: S_ONLY는 청킹과 무관하게 40회, U/SEQ/PAR는 두 프로필에서 각 40회, 총 280개 답변 조건. 질문·모델·출력 한도·기본 검색 설정 고정. PAR는 모든 구조화 일치 카드와 U 후보를 합치고, 사실/검색 근거 단위를 원질문으로 재정렬한다. 카드 점수는 최대 근거 점수이며 근거 수가 많은 카드의 유리함을 별도 기록한다. SQL 순서로 후보를 임의 절단하지 않는다. BGE 순위 때문에 적합 카드가 top3에서 빠지는 사례가 있을 때만 동일 후보에 대한 LLM 선택 대안을 전 문항으로 비교한다.
4. **53 순차 근거 전달 재검사**: 결과를 보기 전에 선정한 12문항 × 두 프로필 × A/B × 2회, 최대 96개 답변 조건. A는 카드 범위와 U 근거만, B는 동일한 U 검색·순위·근거를 유지한 채 일치 DB 사실을 답변 입력에 추가한다. 원질문/검색 입력은 바꾸지 않는다. 입력이 같으면 같은 회차에서만 답변을 공유해 무승부 처리한다. 64KB 때문에 추가할 수 없는 경우도 전체 분모에 남긴다. B는 질문 단위 개선이 있고 악화·중요 오정보·조건 손실·범위 위반이 없을 때만 선택한다.
5. **54 신규 질문 확인**: 설정 동결 뒤 같은 106개 문서에 대한 새 32문항, 3회 반복. 혜택 8/복합·상세 8/발급사·상품 8/숫자 4/부정 4. 추출 96회, 최대 672개 답변 조건. 반복 간 답변 공유 금지. 정답 카드는 원문으로 확인하고 추가 유효 카드도 원문 판정 후 허용한다. U보다 질문 단위 순개선이 있고 하위 집단 악화·중요 오정보·조건 손실·범위 위반이 없는 후보만 제안한다. 운영 반영은 수행하지 않는다.

## 고정 설정과 비용

운영 benefit/parent-child 프로필을 읽어 사용한다. 청크 크기·토큰 한도는 바꾸지 않는다. 부모 묶음 최대 5, 근거 최대 5개/카드, 답변 입력 64,000바이트, 구성 검색 깊이 50, 후보 20, 상위 카드 3, Vector/BM25 0.4/0.6, CPU 4스레드, BGE 한 인스턴스. gpt-6-luna medium, 추출 출력 3,000/답변 출력 2,400, API 네트워크 재시도 0, 답변 검증 재시도 최대 1. 임베딩은 text-embedding-3-small 1,536차원, 질문만 신규 생성한다.

요청마다 입력·스키마·코드 해시와 물리 요청 수, 전송/캐시/출력 토큰, 실패·재시도 비용을 저장하고 다음 요청 비용을 보수적으로 예약한다. 비용 불명확 시 중단한다. 모든 최악 요청 수가 예산에 들어간다고 가정하지 않는다.

## 시간 측정 계약

API 호출 실제 경과 시간, 논리 답변의 재시도 포함 완료 시간, 조건 추출·DB·임베딩·검색·재정렬·답변 생성 시간을 구분한다. 캐시 재생 시간과 최초 실행 시간을 섞지 않는다. 평균·중앙값·P95(정렬한 n개 중 ceil(0.95n)번째)·최대값과 실패 수를 함께 제시한다. 연속 실행을 실제로 계측하지 않은 전체 시간은 **단계 시간 합계**로 표시하고 사용자 질의부터 출력까지 실측값이라고 부르지 않는다. 스트리밍을 사용하지 않으므로 첫 토큰 시간과 브라우저 표시 시간은 **미측정**이다. CPU·최대 RSS·가용 RAM·GPU·캐시/색인 크기도 기록한다.

## 결과물과 한계

노트북은 notebooks/의 번호 ipynb, 공유 실험 도우미와 의미 있는 회귀 검사는 notebooks/scripts/, 데이터와 실행 기록은 notebooks/data/번호_이름/, 직접 작성한 HTML은 docs/report/동일번호_이름_report.html에 둔다. HTML 생성 스크립트는 만들지 않는다. 반복·재개·예산 제어 및 동일 SQL 계약의 재사용만 도우미로 분리한다. 개발 집합을 여러 번 본 결과와 신규 확인 결과를 구분하고, 청크/사실 분모가 다른 Recall/nDCG를 직접 비교하지 않는다. 마지막에 선정·미선정·운영 미반영 상태와 다음 단계를 명시한다.

## 52번 조회 오류 발견 후 별도 재실행

기존 52번은 239/280 검색, 답변 0/280에서 중지했다. 예외 문장에 대상 단어가 있다는 이유만으로 긍정적 포함 특례와 부분 제외까지 혜택 전체에서 제외하는 오류를 확인했다. `52_query_predicate_correction.py`가 현재 프로세스의 사실 판정만 대체하고 원50/51/52 코드·DB·기록은 보존한다. 51번 첫 추출은 그대로 재조회한다. 개발 추출 51종 요구사항에서 달라진 187쌍/75사실을 모두 검토했고, 전체 대상 제외로 잘못 추가된 사례는 이 목록에서는 확인되지 않았다. 독립 인간 검증이나 OCR 정확도 증명을 의미하지 않는다.

`52_corrected_four_retrieval_modes.ipynb`는 U 본문만 기존 계약/범위/벡터/색인을 검증해 재사용하고 새 계약에 묶는다. S_ONLY/SEQ/PAR는 수정 조회로 새로 실행한다. 기존 질문 임베딩 비용 0.000005080달러는 stage520으로 한 번만 집계하고, 수정 실행 상한은 1.999994920달러로 두어 52번 전체 상한 2달러를 유지한다. 53은 수정52 결과만 사용한다. 54의 신규 질문은 유료 답변 전에 동일한 판정 차분 원문 검토를 다시 실시한다. 현재 수정은 예외 문장 전체 거절에만 한정되며 별칭·숫자 적재의 모든 한계가 해결되었다고 보지 않는다.
