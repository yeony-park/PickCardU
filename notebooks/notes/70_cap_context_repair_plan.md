# 70: 대상 이용금액 문맥 복구 후 개발 재검증

69번의 원문 감사에서 발견한 구조화 사실 충돌을 보존하고, 승인된 비교의 미실행 답변 432건을 별도 개발 실험으로 진행한다. 운영 반영과 독립 확인시험은 아니다. proposal-reviewer의 조건부 검토를 반영했다.

## 변경과 고정

- 69번은 원문 gate 거절·답변 생성 0건으로 종료한다. 기존 DB/보고/답변/원문은 덮어쓰지 않는다.
- 68번의 잘못된 cap 문맥에 노출된 60개 실제 화면 답변을 원래 66번 정책으로 재검토한다. 기술실패 7건은 유지하고, 미요청 설명 생략만으로 실패시키지 않는다. 나머지 372건과 합쳐 원래 선택 규칙을 다시 적용한다. 입력 노출 자체를 오답으로 간주하지 않는다.
- 복사 DB5에서 전 3,403행에 동일한 출처 문맥 규칙을 적용한다. 원문 같은 행의 정확한 cap fragment와 그 앞의 명시적 '할인받기 전 이용금액 기준' 문구가 연결될 때만 대상 이용금액으로 구분한다. 식별자·질문별 예외, 새 동의어, 오타 보정은 없다.
- raw_fact와 원문은 유지한다. 정규화 fields.cap에는 원문 qualifier와 자기 fragment를 함께 기록하고 지급한도 derived는 unknown으로 둔다. 계산한 할인액을 원문 지급한도로 저장하지 않는다. 실제 LLM 입력에도 이 문맥이 보존되어야 한다.
- 모든 변경행을 원문과 대조한다. 새 DB SQL을 전부 재실행하고 기존/신규 카드 범위와 witness를 비교한다.
- 69의 원질문 24개, 추출 72개, 임베딩 24개를 정확한 해시 결속 후 재사용한다. 검색은 질문·벡터·프로필·색인·범위가 같은 경우에만 재사용한다. 범위가 다르면 원질문으로 다시 검색한다.
- 기존 U, 현재 SEQ65, DB5 수정 순차 × 두 운영 프로필 × 세 반복 = 432개 답변을 새로 생성한다. 검색 프로필·reranker·프롬프트·스키마·모델·출력 한도는 기존 선택 설정으로 고정한다. 구조화 양성이면 그 카드 범위에서 U 한 번, 0건이면 원래 범위 U 한 번이다.
- 실제 추가 fact 전부의 소유자·필드·관계·serialized 본문을 감사한다. 충돌 0·미검토 0·정답표 자동조립 미사용을 답변 생성 gate로 강제한다.

## 판정과 자원

- 66 정책의 직접 요구 충족, 실제 주장 정확성, 입력 지원, 추가 설명을 구분한다. 화면은 본문과 카드 추천 이유다. 숨은 claims가 화면 누락을 보충하지 않는다.
- 전체 432개, 질문 하위집단, 질문별 승패, 세 반복 변동을 공개한다. 질문 블록 bootstrap 10,000회·seed70·95% 구간은 개발 자료 진단이다. 같은 질문 반복을 독립 질문으로 세지 않는다.
- 69에서 이미 원인과 질문을 확인했으므로 사후 수정 개발 결과다. 알려진 원U의 Monthly 150만원/50만원 충돌은 남아 있으며 운영 승격을 허용하지 않는다.
- gpt-6-luna medium, 답변 2,400 출력 토큰, 논리당 최대 두 물리 시도. 답변 432논리/최대864물리, 새 추출·임베딩 API 0. 누적 8달러, 시작 보수 차감 2.168031040달러, 잔여 5.831968960달러. 실제 payload의 최악 비용 예약 후 실행하며 새 사용량 미확인 시 중단한다.
- 단가 기반 사용량 비용과 청구서를 구분하고, 재사용/새 호출, 답변 준비 시간, provider 왕복, CPU/메모리를 기록한다. TTFT·화면 표시·미측정 전체 검색 시간은 추정하지 않는다.
- notebooks 루트는 ipynb만, 공유·재개 검증 helper/tests는 scripts, 자료는 data, 계획은 notes에 둔다. 보고서 HTML은 main이 직접 작성한다. 운영 코드와 원본 PDF/OCR/DB/색인은 읽기 전용이다.

## 완료 조건

원본 보존 및 재검토/새 DB 출처 gate 통과 → 새 432답변 → 실제 화면 의미 판정 → 전체 조건 비교/비용·시간 보고 → 등록 reviewer 검토 → 이번 변경만 선택 커밋. gate가 통과하지 못하면 차단 원인을 보존·보고하고 통과로 바꾸지 않는다.

## 실행 결과와 선택

- 68의 노출 60답변을 재검토하고 432개 전체를 재결속해도 예비 선택은 유지됐다. DB5는 3행을 변경하고 3,400행을 보존했다. 추가 사실 55개·1,650필드·325전송을 검토하고 gate 수락 후 실행했다.
- 432논리 답변/438물리 시도 중 431개가 기술 성공했다. 최종 EOF 실패 1개는 전체 분모에 남겼다. 24질문 모두 본문과 추천 이유를 문장별 검토하고, 원문 참조 717개와 실제 전송 입력을 결속했다. 코드의 해시 검사는 의미상 정답 판정을 대신하지 않는다.
- 전체72개 기준 U/기존순차/수정순차 통과는 benefit 68/71/65, parent-child 62/67/60이다. 수정 순차는 새 확정 수치·관계 오류가 있어 미채택한다. 기존 순차를 개발 기준선으로 유지하고 운영은 변경하지 않는다.
- 자동 사실 추가는 97/144개 수정 순차 입력에 적용됐다. 적용 묶음만 보거나 정확성 표현 모호성을 완화해도 수정 순차의 우위는 나타나지 않았다. 수정 조회+카드 범위만 전달하는 조건은 이번 생성 비교에 없었다.
- 기존 Monthly 리워드 충돌 외에 UniMile 플랫폼 네이버페이의 PDF 적립 제공/OCR 적립 제외 충돌도 발견했다. 후자는 추가 사실 55개가 아닌 기존 U에 있으며 1개 답변이 이를 전파했다. 원본·입력·기존 gate를 변경하지 않고 별도 원문 경로 감사와 공통 질문 민감도로 보존했다.
- 새 API 사용량 환산 $0.402066920, 누적 보수 차감 $2.570097960, $8 중 잔여 $5.429902040. 과거 미확인2건 예약 $0.006234500은 누적에 포함되며 청구서 실측이 아니다. 답변 생성 전체120.18분, CPU1,349.90초, 생성 프로세스 최고RSS1,140.59MiB다. 온라인 새 검색부터의 전체 지연·첫 토큰·브라우저 표시 시간은 미측정이다.
- 후속은 올바른 입력의 카드·혜택·수치 관계를 유지하는 생성 비교, 원문과 반대인 OCR 파생자료 수정 후 재검증, 필요한 본문이 없는 사례의 검색 보완이다. 이번 범위에서 추가 API 실험이나 운영 수정은 하지 않았다.
- 전체 노트북 재실행 대신 단계별·추가 셀을 실행했다. 결과와 재현 한계는 [직접 작성한 70 HTML](../../docs/report/70_cap_context_repair_report.html), 실제 판정은 `../data/70_cap_context_repair/manual_reviews.json`, 집계는 같은 폴더 `evaluation_summary.json`에 보존한다.
